## 2. 最终结论

设计整体合理，可以作为 MVP 开工基线，但有四项必须在开发前验证：

1. RTX 5090 宿主机驱动、NVIDIA Container Toolkit 与固定 vLLM 镜像的实际兼容组合；
2. llm-d Planner 固定 Commit 的 API、Python 版本和 RTX 5090 自定义显存输入行为；
3. 目标 EvalScope 固定版本的 Python API、Progress Tracker 和输出字段；
4. 首批目标模型在 vLLM/5090 上的 Kernel 与量化兼容性。

这些内容不能仅靠文档推断，必须在 Phase 0 真机验证。

## 6. 工具职责准确性检查

### 6.1 NVML

准确描述：

- GPU 状态程序化接口；
- `nvidia-smi` 底层使用 NVML；
- 对 GeForce/RTX 支持有限；
- MVP 不使用写控制方法。

来源：

- https://docs.nvidia.com/deploy/nvml-api/nvml-api-reference.html

### 6.2 llm-d Planner

准确描述：

- 项目位于 llm-d incubation；
- Capacity Planner 估算权重、KV、激活和系统开销；
- 支持模型 Fit、最大上下文和并发；
- 提供 CLI/API；
- 还包含 GPU Recommender 和 Kubernetes 方向，但 MVP 不使用；
- 项目仍在演进，需要固定 Commit。

来源：

- https://github.com/llm-d-incubation/llm-d-planner

### 6.3 vLLM

准确描述：

- 有官方 Docker 镜像；
- 可启动 OpenAI-compatible Server；
- Docker 需要 GPU Runtime；
- MVP 固定镜像而非 `latest`。

来源：

- https://docs.vllm.ai/en/latest/deployment/docker/
- https://docs.vllm.ai/en/stable/getting_started/installation/gpu/

### 6.4 EvalScope

准确描述：

- Closed-loop 由 `parallel` 限制在途请求；
- Open-loop 使用 Rate，不等待完成，忽略 Parallel；
- `number` 需要和扫描变量一一对应；
- Stream 用于 TTFT；
- Duration 是 Soft Exit；
- 支持 SLA Auto-Tune；
- 支持 Progress Tracker（具体稳定性需固定版本验证）。

来源：

- https://evalscope.readthedocs.io/en/latest/user_guides/stress_test/parameters.html

### 6.5 Optuna

准确描述：

- 负责 Study/Trial 和采样；
- Pruner 通用模块当前预期用于单目标；
- 本设计采用单目标 + 硬约束；
- 部署/测试不是 Optuna 自动完成。

来源：

- https://optuna.readthedocs.io/en/stable/
- https://optuna.readthedocs.io/en/stable/reference/pruners.html

### 6.6 MLflow

准确描述：

- Tracking 记录参数、代码版本、指标和 Artifact；
- Run 属于 Experiment；
- 支持 Backend Store 和 Artifact Store；
- 不把 MLflow 描述成自动 Champion 算法。

来源：

- https://mlflow.org/docs/latest/tracking

### 6.7 OPA

准确描述：

- OPA 返回策略决策；
- Decision Log 可审计；
- 可 Mask 敏感字段；
- OPA 不执行 Docker；
- AI 不能自授权。

来源：

- https://www.openpolicyagent.org/docs
- https://www.openpolicyagent.org/docs/management-decision-logs

## 7. 关键修正记录

### 修正一：每环节一个工具

原始表达容易误解为“每环节只给 AI 一个 Tool”。

最终定义：

> 每个环节一个主要外部项目；一个能力包；多个窄 Agent Tool。

### 修正二：MLflow

不再表述为：

> MLflow 选择最优。

最终为：

> MLflow 保存和查询证据；Champion Policy 自研。

### 修正三：OPA

不再表述为：

> AI 调用 OPA 决定自己是否有权限。

最终为：

> Tool Gateway 强制调用 OPA；AI 只能发起审批。

### 修正四：Agent 自由度

不是完全锁死，也不是任意参数。

最终为：

- Preset；
- Guided；
- Expert 白名单 Override。

### 修正五：长任务

不使用同步长调用。

最终为：

- Start；
- Status；
- Result；
- Cancel。

## 12. 合理性结论

本设计采取的不是“让 AI 自由操作所有工具”，也不是“把流程写死到无法适应场景”，而是：

```text
AI 自由：
- 理解目标
- 选择领域模式
- 提议参数范围
- 解释结果
- 决定需要哪类补充实验

系统确定：
- 参数是否合法
- 是否可见
- 是否授权
- 如何编译
- 如何执行
- 如何加锁
- 如何记录
- 如何判断约束
- 如何选择 Champion
```

这一边界适合客户环境中的高成本 GPU 操作，也保留了场景适配能力。
