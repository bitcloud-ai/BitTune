# 08. 测试验收与实施路线

## 1. 测试目标

不仅验证“代码能跑”，还要验证：

- 领域 Schema 可以阻止非法调用；
- Agent 不能越权；
- 外部项目结果被正确归一化；
- 长任务可取消和恢复；
- 失败后资源被回收；
- 最终结论可复现；
- 单卡结果没有被 Agent 模型或其他 GPU 进程污染。

## 3. Golden Test

### 3.1 Compiler Golden

给定领域 Plan，输出必须与 Golden JSON 一致。

例如：

```text
closed_loop [1,2,4], requests_per_worker=5
→ parallel [1,2,4]
→ number [5,10,20]
```

### 3.2 Metric Golden

固定一份 EvalScope 原始报告，检查：

- 单位；
- 百分位；
- 成功率；
- Window Completion；
- TPM/RPM；
- 输入输出 Token。

### 3.3 Policy Golden

- L0 允许；
- L2 无审批拒绝；
- L2 Hash 匹配允许；
- L2 自审批、Service 审批、非 Admin 审批、过期和 Experiment/Plan/Action 错配均拒绝；
- L3 永远拒绝；
- 时长、请求、输入 Token、输出 Token 和磁盘增长任一预算超限均拒绝。

## 5. 性能测试基线

MVP 标准 Workload：

| ID | 输入 | 输出 | 用途 |
|---|---:|---:|---|
| `short-v1` | 512 | 256 | 低延迟 |
| `medium-v1` | 2048 | 512 | 主场景 |
| `long-v1` | 8192 | 512 | 长上下文 |

标准测试顺序：

1. 1 请求 Smoke；
2. 5 请求 Baseline；
3. 并发 1/2/4/8；
4. 根据闭环结果估算 Open Loop Rate；
5. 3～5 个 Rate；
6. 进入调优。

## 6. 结果稳定性

建议：

- 每档 Warmup 10%；
- 相邻测试休息；
- 固定 Seed；
- 固定 Prompt 集；
- 固定采样；
- 检查 GPU 温度和功耗；
- Top 3 重复至少 2 次；
- 如果变异系数过高，不选 Champion，先标记环境不稳定。

首版可定义：

```text
CV = standard_deviation / mean
```

若核心 Objective 的 CV > 5%（初始经验阈值，需要现场校准），结论标记低置信度。该阈值不是通用行业标准，应作为可配置策略。

## 11. 最终退出标准

MVP 可进入下一阶段，必须同时满足：

- 功能验收全部通过；
- 无任意 Shell；
- 任务可恢复；
- 结果可复现；
- 至少一个模型完成完整闭环；
- 至少一次 OOM/失败被安全处理；
- 文档、Schema 和代码一致；
- 对单卡和估算限制说明清楚；
- 性能结论不夸大为全局最优。
