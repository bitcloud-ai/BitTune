# 04. 七个环节能力与接口详细设计

## 1. 总览

| 环节 | 主要项目 | 能力包 | AI 可见 Tool 数 |
|---|---|---|---:|
| 环境检测 | NVIDIA NVML | `environment` | 5 |
| 容量规划 | llm-d Planner | `capacity` | 1 |
| 模型部署 | vLLM | `deployment` | 5 |
| 性能测试 | EvalScope | `benchmark` | 5 |
| 参数调优 | Optuna | `optimization` | 5 |
| 收敛与证据 | MLflow | `evidence` | 3 |
| 安全控制 | OPA | `approval` | 2 |

注意：AI 可见 Tool 不是底层项目 API 数量。大多数内部操作不暴露。

# 2. 环节一：环境检测

## 2.1 选择

主要外部项目：NVIDIA NVML。

理由：

- NVML 是 NVIDIA GPU 状态的程序化接口；
- `nvidia-smi` 本身基于 NVML；
- 比解析人类可读 CLI 更稳定；
- 对 RTX/GeForce 是有限支持，因此只依赖其可稳定查询字段；
- CPU、内存、磁盘、Docker 和 OS 由你们的 Host Collector 补充。

## 2.2 能力包

```text
EnvironmentCapability
├── NVMLCollector
├── LinuxHostCollector
├── DockerGpuProbe
├── CompatibilityRules
└── HardwarePassportBuilder
```

## 2.3 AI 可见 Tool

### `create_environment_plan`

输入：

```json
{
  "scope": "mvp_full",
  "include_runtime_probe": true
}
```

输出不可变的检测 Plan、资源预算和 Plan Hash。该 Tool 不执行 Runtime Probe。

### `start_environment_inspection`

只接收已保存的 `environment_plan_id` 和预期 Plan Hash，返回异步 Job：

```json
{
  "inspection_id": "env_01J...",
  "job_id": "job_01J...",
  "status": "queued"
}
```

### `get_environment_status`

输入 `job_id`，返回统一 Job 状态和进度。

### `get_environment_result`

输入：`job_id`。

输出：

- 标准化摘要；
- 风险；
- 支持能力；
- Artifact Ref。

### `cancel_environment_inspection`

输入 `job_id`，停止未完成的 Runtime Probe，保留已产生的审计和 Artifact。

## 2.4 内部能力

- NVML 初始化和字段查询；
- GPU 型号、UUID、显存、温度、功耗、利用率、进程；
- `/proc/cpuinfo`、`/proc/meminfo`；
- `sysfs` 和磁盘空间；
- Docker/Compose 版本；
- NVIDIA Container Toolkit Probe；
- 启动临时 CUDA 容器执行只读 GPU 验证；
- 兼容性规则；
- Hardware Passport 签名。

## 2.5 不暴露给 AI

- `nvmlDeviceSet*` 控制方法；
- 功耗上限修改；
- 时钟修改；
- 任意系统命令；
- 驱动安装；
- 包管理器；
- 结束其他 GPU 进程。

## 2.7 合理性限制

NVML 不等于完整硬件诊断。MVP 只承诺：

- GPU 可见性和运行状态；
- 单卡部署前检查；
- 环境快照。

不承诺：

- 数据中心级深度诊断；
- NCCL 多卡带宽；
- ECC 完整健康；
- 多 NUMA/PCIe 优化。

未来可增加 DCGM/NCCL Adapter，但不改变 `HardwarePassport`。

# 3. 环节二：模型与容量规划

## 3.1 选择

主要项目：llm-d Planner 的 Capacity Planner。

使用范围：

- Hugging Face 模型配置解析；
- 权重、KV Cache、激活和系统开销估算；
- 模型是否装得下；
- 最大上下文和并发估算；
- 合法 TP 值分析，但 MVP 固定 TP=1。

不使用其 Kubernetes 部署能力。

## 3.2 风险

llm-d Planner 位于 incubation 组织，必须：

- 固定 Commit；
- 对 API 做 Anti-Corruption Adapter；
- 不把估算当实测；
- 5090 不在其常见数据中心 GPU Benchmark 集时，显式标记为估算；
- 保留后续替换 Planner 的能力。

## 3.3 AI 可见 Tool

### `create_capacity_plan`

输入：

```json
{
  "model_ref": {
    "type": "huggingface",
    "id": "Qwen/...",
    "revision": "immutable-commit"
  },
  "hardware_passport_id": "env_...",
  "deployment_constraints": {
    "tensor_parallel_size": 1,
    "max_model_len": 8192,
    "gpu_memory_utilization": 0.90
  },
  "workload": {
    "expected_concurrency": 8,
    "prompt_tokens_p95": 4096,
    "output_tokens_p95": 512
  }
}
```

输出不可变 Capacity Plan，其中包含 Model Profile Ref、估算、2～5 个 Candidate、Provider/Schema Version 和 Plan Hash：

```json
{
  "fit": true,
  "source": "estimated",
  "confidence": "medium",
  "memory": {
    "weights_gb": 0,
    "kv_cache_budget_gb": 0,
    "activation_gb": 0,
    "overhead_gb": 0
  },
  "limits": {
    "estimated_max_context": 0,
    "estimated_concurrency": 0
  },
  "requires_benchmark_validation": true
}
```

Candidate 类型固定为：

- 保守；
- 均衡；
- 吞吐优先。

## 3.4 内部能力

- 下载/读取 `config.json`；
- 解析模型架构；
- 调用 Capacity Planner；
- 应用 RTX 5090/MVP 限制；
- 添加安全余量；
- 过滤不支持的量化和 TP；
- 生成 Candidate；
- 生成估算证据。

# 4. 环节三：模型部署

## 4.1 选择

主要项目：vLLM 官方 OpenAI-Compatible Server 容器。

MVP 固定：

- 单模型；
- 单卡；
- TP=1；
- Docker；
- OpenAI-compatible endpoint；
- 固定镜像 Digest；
- 每次只有一个被测模型实例。

## 4.2 AI 可见 Tool

### `create_deployment_plan`

输入 Candidate ID，输出：

- 规范化参数；
- 预计显存；
- 模型下载量；
- 端口；
- 将停止的现有部署；
- 风险和审批级别；
- Plan Hash。

### `start_deployment`

只接收已保存 `deployment_plan_id` 和 Hash。

### `get_deployment_status`

返回：

- queued/starting/healthy/unhealthy/stopped/failed；
- 健康检查；
- 模型；
- Endpoint；
- 日志摘要。

### `cancel_deployment`

只接收操作为 `shutdown` 的已审批 Deployment Plan ID 和 Hash，需要 L2 审批。

### `get_deployment_result`

返回脱敏、限制大小的日志摘要和 Artifact Ref。

## 4.3 内部架构

```text
DeploymentService
  ├── CandidateValidator

  ├── ImageResolver
  ├── ModelCacheManager
  ├── GpuLockManager
  ├── DockerAdapter
  ├── HealthChecker
  └── RollbackManager
```

## 4.4 参数分层

### 固定参数

- 镜像；
- 容器用户；
- 网络；
- IPC；
- 缓存目录；
- 日志目录；
- GPU 设备；
- Endpoint；
- Revision。

### 领域可调参数

- `max_model_len`
- `gpu_memory_utilization`
- `max_num_seqs`
- `max_num_batched_tokens`
- `enable_chunked_prefill`

### 禁止 AI 直接设置

- `--privileged`
- 任意 Volume；
- 任意 EntryPoint；
- 任意环境变量；
- 任意网络模式；
- `trust_remote_code`；
- 宿主机路径；
- Docker Socket。

## 4.5 部署状态机

```text
planned
→ waiting_approval
→ queued
→ acquiring_gpu
→ pulling_image
→ preparing_model
→ starting
→ health_checking
→ healthy
→ stopping
→ stopped

任意阶段 → failed
```

## 4.6 健康检查

1. 容器进程存在；
2. HTTP Health；
3. `/v1/models`；
4. 最小 Chat Completion；
5. 返回非空内容；
6. NVML 显存符合预期；
7. 日志无 OOM/Fatal。

## 4.7 回滚

MVP 回滚含义：

- 停止失败容器；
- 清理临时资源；
- 释放 GPU 锁；
- 恢复前一个已知良好 Deployment（如果用户选择）；
- 不自动删除模型缓存。

# 5. 环节四：性能测试

## 5.1 选择

主要项目：EvalScope。

首版支持：

- baseline；
- closed-loop sweep；
- open-loop sweep；
- SLA search；
- 固定长度或本地标准数据集；
- 流式接口；
- OpenAI-compatible Chat Completions。

## 5.2 AI 可见 Tool

### `create_benchmark_plan`

领域输入，不接受 EvalScope CLI。

### `start_benchmark`

只接受 Plan ID 和 Hash。

### `get_benchmark_status`

统一 Job 状态。

### `get_benchmark_result`

返回标准化指标和原始 Artifact Ref。

### `cancel_benchmark`

有界停止，不删除历史结果。

## 5.3 WorkloadSpec

```json
{
  "schema_version": "workload/v1",
  "dataset": {
    "type": "synthetic_fixed",
    "dataset_id": "fixed-2k-512-v1"
  },
  "prompt_tokens": 2048,
  "output_tokens": 512,
  "stream": true,
  "ignore_eos": true,
  "sampling": {
    "temperature": 0,
    "seed": 20260805
  }
}
```

## 5.4 四种模式转换

### Baseline

领域：

```json
{"mode": "baseline", "requests": 5}
```

编译：

```text
parallel=[1]
number=[5]
rate=-1
open_loop=false
```

### Closed Loop

领域：

```json
{
  "mode": "closed_loop_sweep",
  "concurrency_levels": [1, 2, 4, 8],
  "requests_per_worker": 5
}
```

编译：

```text
parallel=[1,2,4,8]
number=[5,10,20,40]
rate=-1
open_loop=false
```

`number` 的策略由产品定义并记录，不让 AI 手工维护一一对应关系。

### Open Loop

领域：

```json
{
  "mode": "open_loop_sweep",
  "request_rates": [0.5,1,2,4],
  "duration_seconds": 120
}
```

编译：

```text
open_loop=true
rate=[0.5,1,2,4]
parallel=ignored
number=ceil(rate * duration * number_safety_factor)
duration=120
```

必须设置总请求和 Token 上限。

### SLA Search

领域：

```json
{
  "mode": "sla_search",
  "search_variable": "rate",
  "lower_bound": 1,
  "upper_bound": 20,
  "runs_per_level": 3,
  "constraints": [
    {"metric": "p99_ttft_ms", "operator": "<=", "value": 2000}
  ]
}
```

Compiler 转换为 EvalScope SLA 参数，并进行指标单位转换。

## 5.5 关键校验

- 开环 Rate 必须 >0；
- 开环忽略并发，不允许用户同时指定并发扫描；
- `number` 数组长度必须和扫描变量一致；
- 测 TTFT 必须流式；
- `duration` 是 Soft Exit，需要区分调度窗口和最终完成时间；
- 固定 Token 测试要记录 `ignore_eos`；
- 数据集和 Tokenizer 固定；
- 测试不能超过 Token Budget；
- 同一 Trial 的 WorkloadSpec 必须一致；
- Warmup 不计入指标。

## 5.6 结果归一化

必须记录：

- Submitted；
- Completed；
- Failed；
- Timed out；
- Duration；
- Window Completion；
- RPS/RPM；
- Input/Output Token Throughput；
- TTFT/TPOT/ITL/E2E；
- 输入和输出长度分布；
- 原始报告 Hash。

## 5.7 不暴露给 AI

- EvalScope 全部 CLI；
- 任意 `extra_args`；
- 任意 URL；
- 任意 Header；
- 任意数据文件路径；
- 无上限的 Rate；
- 直接修改输出目录。

# 6. 环节五：参数调优

## 6.1 选择

主要项目：Optuna。

Optuna 负责：

- 采样参数；
- Study/Trial；
- 存储；
- 单目标搜索；
- 根据结果记录完成或失败。

你们的 Optimization Controller 负责：

- 部署；
- Benchmark；
- 预算；
- 参数合法性；
- Trial 回收；
- 结果提交；
- 收敛。

## 6.2 AI 可见 Tool

### `create_optimization_plan`

输入：

- Base Candidate；
- Search Space Profile；
- Workload/SLO；
- Trial/时间/Token 预算。

### `start_optimization`

需要审批，返回 Job ID。

### `get_optimization_status`

返回 Trial 进度。

### `get_optimization_result`

返回满足约束的 Top N。

### `cancel_optimization`

完成当前安全点后停止。

```json
{
  "objective": {

      "type": "float",
      "low": 0.80,
      "high": 0.94,
      "step": 0.02
    },
    "max_num_seqs": {
      "type": "categorical",
      "choices": [4, 8, 16, 32]
    },
    "max_num_batched_tokens": {
      "type": "categorical",
      "choices": [2048, 4096, 8192, 16384]
    },
    "enable_chunked_prefill": {
      "type": "categorical",
      "choices": [true, false]
    }
  }

```

## 6.4 Trial 流程

```text
Optuna ask
→ Candidate Validator
→ 静态裁剪
→ 部署
→ 健康检查
→ Benchmark
→ Constraint Evaluation
→ MLflow Logging
→ Optuna tell
→ Cleanup
```

## 6.5 Trial 状态

- `suggested`
- `rejected_static`
- `deployment_failed`
- `benchmark_failed`
- `oom`
- `constraint_failed`
- `completed`
- `cancelled`

失败 Trial 也必须保存原因，不可静默消失。

## 6.6 Pruning

Optuna 通用 Pruner 当前主要面向单目标中间值。MVP 第一版不依赖“Benchmark 中途的多目标 Pruning”，采用：

- 静态裁剪；
- OOM 边界裁剪；
- 明显违反硬约束时终止该 Trial；
- 单目标 Objective；
- 约束作为可行性判断。

## 6.7 AI 不可调用

- `trial.suggest_*`；
- `study.tell`；
- 直接修改 Storage；
- 直接决定 Trial 指标；
- 跳过 Benchmark；
- 修改固定模型/数据集。

# 7. 环节六：收敛、选择和证据

## 7.1 选择

主要项目：MLflow Tracking。

准确边界：

- MLflow 存参数、指标、Artifact、Run；
- MLflow 提供查询和比较；
- **你们自研 Champion Policy**；
- AI 只解释，不生成指标。

## 7.2 AI 可见 Tool

### `get_trial_comparison_result`

返回标准化对比表。

### `create_champion_plan`

由确定性 Policy 先筛选并生成不可变 Champion Plan，包含 Champion、Fallback、证据完整性和 Plan Hash。

### `get_evidence_result`

读取已归档的 Evidence Summary，返回 Evidence Bundle 和报告 Artifact Ref。

## 7.3 自动记录，不作为 AI Tool

每个 Run 自动记录：

- Hardware Passport ID/Hash；
- 模型 Revision；
- 镜像 Digest；
- vLLM 参数；
- WorkloadSpec Hash；
- EvalScope 版本；
- 指标；
- 日志；
- 原始报告；
- 失败原因；
- 时间；
- 代码版本。

## 7.4 Convergence Policy

停止条件任一满足：

- Trial Budget 耗尽；
- Wall-clock Budget 耗尽；
- Token Budget 耗尽；
- 连续 N 个有效 Trial 改善低于阈值；
- 搜索空间有效组合耗尽；
- 用户取消；
- 基础设施阻断。

不能因为 LLM 说“差不多了”而停止。

## 7.5 Champion Policy

1. 过滤无效/失败 Trial；
2. 过滤未满足全部硬约束；
3. 过滤证据不完整；
4. 按目标指标排序；
5. 对 Top 3 复测；
6. 计算均值、离散度和最差值；
7. 只有显著超过噪声才宣称更优；
8. 输出 Champion + Fallback；
9. 人工批准。

```text
├── slo.json
├── candidates/
├── trials/
├── verification/
├── champion.json
├── report.md

```

# 8. 环节七：安全、策略和审批

## 8.1 选择

主要项目：OPA。

OPA 负责根据结构化输入返回策略决策。它不是执行器，也不是 Agent Tool 的直接替代。

## 8.2 AI 可见 Tool

### `start_approval_request`

AI 可以解释为什么需要审批并发起请求。

### `get_approval_status`

查询人审结果。

`explain_rejected_action` 可以由应用层读取 OPA Reason 后生成，不一定作为独立 Tool。

## 8.3 内部强制能力

- `authorize_action`
- `mask_decision_log`
- `record_decision`
- `enforce_limits`
- `require_plan_hash`
- `require_human_approval`

这些不暴露给 AI。

## 8.4 风险等级

| 等级 | 示例 | 默认 |
|---|---|---|
| L0 | 查询结果、创建只读计划 | 自动允许 |
| L1 | 环境检测、模型元数据解析 | 自动允许并审计 |
| L2 | 启停容器、压测、调优、下载模型 | 人工审批 |
| L3 | 驱动、内核、删除模型、任意 Shell | MVP 拒绝 |

## 8.6 合理性

首版 OPA 规则规模很小，但仍有价值：

- 策略与业务代码分离；
- 所有动作统一审计；
- 以后进入客户环境时可扩展角色、时间窗和额度；
- 防止 Agent Prompt 成为唯一安全边界。
