# 2. 环节一：环境检测

## 2.1 选择

主要外部项目：NVIDIA NVML。

理由：

- NVML 是 NVIDIA GPU 状态的程序化接口；
- `nvidia-smi` 本身基于 NVML；
- 比解析人类可读 CLI 更稳定；
- 对 RTX/GeForce 是有限支持，因此只依赖其可稳定查询字段；
- CPU、内存、磁盘、Docker 和 OS 由你们的 Host Collector 补充。

## 2.2 能力包

```text
EnvironmentCapability
├── NVMLCollector
├── LinuxHostCollector
├── DockerGpuProbe
├── CompatibilityRules
└── HardwarePassportBuilder
```

## 2.3 AI 可见 Tool

### `create_environment_plan`

输入：

```json
{
  "scope": "mvp_full",
  "include_runtime_probe": true
}
```

输出不可变的检测 Plan、资源预算和 Plan Hash。该 Tool 不执行 Runtime Probe。

### `start_environment_inspection`

只接收已保存的 `environment_plan_id` 和预期 Plan Hash，返回异步 Job：

```json
{
  "hardware_passport_id": "env_00000000000000000000000000000000",
  "job_id": "job_00000000000000000000000000000000",
  "status": "queued"
}
```

### `get_environment_status`

输入 `job_id`，返回统一 Job 状态和进度。

### `get_environment_result`

输入：`job_id`。

输出：

- 标准化摘要；
- 风险；
- 支持能力；
- Artifact Ref。

### `cancel_environment_inspection`

输入 `job_id`，停止未完成的 Runtime Probe，保留已产生的审计和 Artifact。

## 2.4 内部能力

- NVML 初始化和字段查询；
- GPU 型号、UUID、显存、温度、功耗、利用率、进程；
- `/proc/cpuinfo`、`/proc/meminfo`；
- `sysfs` 和磁盘空间；
- Docker/Compose 版本；
- NVIDIA Container Toolkit Probe；
- 启动临时 CUDA 容器执行只读 GPU 验证；
- 兼容性规则；
- Hardware Passport 签名。

## 2.5 不暴露给 AI

- `nvmlDeviceSet*` 控制方法；
- 功耗上限修改；
- 时钟修改；
- 任意系统命令；
- 驱动安装；
- 包管理器；
- 结束其他 GPU 进程。

## 2.7 合理性限制

NVML 不等于完整硬件诊断。MVP 只承诺：

- GPU 可见性和运行状态；
- 单卡部署前检查；
- 环境快照。

不承诺：

- 数据中心级深度诊断；
- NCCL 多卡带宽；
- ECC 完整健康；
- 多 NUMA/PCIe 优化。

未来可增加 DCGM/NCCL Adapter，但不改变 `HardwarePassport`。

# 3. 环节二：模型与容量规划

## 3.1 选择

主要项目：llm-d Planner 的 Capacity Planner。

使用范围：

- Hugging Face 模型配置解析；
- 权重、KV Cache、激活和系统开销估算；
- 模型是否装得下；
- 最大上下文和并发估算；
- 合法 TP 值分析，但 MVP 固定 TP=1。

不使用其 Kubernetes 部署能力。

## 3.2 风险

llm-d Planner 位于 incubation 组织，必须：

- 固定 Commit；
- 对 API 做 Anti-Corruption Adapter；
- 不把估算当实测；
- 5090 不在其常见数据中心 GPU Benchmark 集时，显式标记为估算；
- 保留后续替换 Planner 的能力。

# 4. 环节三：模型部署

## 4.1 选择

主要项目：vLLM 官方 OpenAI-Compatible Server 容器。

MVP 固定：

- 单模型；
- 单卡；
- TP=1；
- Docker；
- OpenAI-compatible endpoint；
- 固定镜像 Digest；
- 每次只有一个被测模型实例。

## 4.2 AI 可见 Tool

### `create_deployment_plan`

输入 Candidate ID，输出：

- 规范化参数；
- 预计显存；
- 模型下载量；
- 端口；
- 将停止的现有部署；
- 风险和审批级别；
- Plan Hash。

### `start_deployment`

只接收已保存 `deployment_plan_id` 和 Hash。

### `get_deployment_status`

返回：

- queued/starting/healthy/unhealthy/stopped/failed；
- 健康检查；
- 模型；
- Endpoint；
- 日志摘要。

### `cancel_deployment`

只接收操作为 `shutdown` 的已审批 Deployment Plan ID 和 Hash，需要 L2 审批。

### `get_deployment_result`

返回脱敏、限制大小的日志摘要和 Artifact Ref。

## 4.3 内部架构

```text
DeploymentService
  ├── CandidateValidator
  ├── VllmArgumentCompiler
  ├── ImageResolver
  ├── ModelCacheManager
  ├── GpuLockManager
  ├── DockerAdapter
  ├── HealthChecker
  └── RollbackManager
```

## 4.4 参数分层

### 固定参数

- 镜像；
- 容器用户；
- 网络；
- IPC；
- 缓存目录；
- 日志目录；
- GPU 设备；
- Endpoint；
- Revision。

### 领域可调参数

- `max_model_len`
- `gpu_memory_utilization`
- `max_num_seqs`
- `max_num_batched_tokens`
- `enable_chunked_prefill`

当 `enable_chunked_prefill=false` 时，必须满足
`max_num_batched_tokens >= max_model_len`；Candidate Schema、Deployment Validator 和编译结果
反序列化均执行该交叉校验，违反时直接拒绝。

### 禁止 AI 直接设置

- `--privileged`
- 任意 Volume；
- 任意 EntryPoint；
- 任意环境变量；
- 任意网络模式；
- `trust_remote_code`；
- 宿主机路径；
- Docker Socket。

## 4.5 部署状态机

```text
planned
→ waiting_approval
→ queued
→ acquiring_gpu
→ pulling_image
→ preparing_model
→ starting
→ health_checking
→ healthy
→ stopping
→ stopped

任意阶段 → failed
```

## 4.6 健康检查

1. 容器进程存在；
2. HTTP Health；
3. `/v1/models`；
4. 最小 Chat Completion；
5. 返回非空内容；
6. NVML 显存符合预期；
7. 日志无 OOM/Fatal。

## 4.7 回滚

MVP 回滚含义：

- 停止失败容器；
- 清理临时资源；
- 释放 GPU 锁；
- 恢复前一个已知良好 Deployment（如果用户选择）；
- 不自动删除模型缓存。

## 5.1 选择

主要项目：EvalScope。

首版支持：

- baseline；
- closed-loop sweep；
- open-loop sweep；
- SLA search；
- 固定长度或本地标准数据集；
- 流式接口；
- OpenAI-compatible Chat Completions。

### `start_benchmark`

只接受 Plan ID 和 Hash。

### `get_benchmark_status`

### `get_benchmark_result`

## 5.4 四种模式转换

### Baseline

领域：

```json
{"mode": "baseline", "requests": 5}
```

编译：

```text
parallel=[1]
number=[5]
rate=-1
open_loop=false
```

### Closed Loop

领域：

```json
{
  "mode": "closed_loop_sweep",
  "concurrency_levels": [1, 2, 4, 8],
  "requests_per_worker": 5
}
```

编译：

```text
parallel=[1,2,4,8]
number=[5,10,20,40]
rate=-1
open_loop=false
```

`number` 的策略由产品定义并记录，不让 AI 手工维护一一对应关系。

### Open Loop

领域：

```json
{
  "mode": "open_loop_sweep",
  "request_rates": [0.5,1,2,4],
  "duration_seconds": 120
}
```

编译：

```text
open_loop=true
rate=[0.5,1,2,4]
parallel=<不存在>
number=ceil(rate * duration * number_safety_factor)
duration=120
```

Open-loop 领域 Schema 和编译 DTO 均不存在 `parallel` 字段。输入额外携带 `parallel` 时按
`extra="forbid"` 拒绝，不能静默忽略。必须设置总请求、输入 Token、输出 Token 和持续时间上限。

### SLA Search

领域：

```json
{
  "mode": "sla_search",
  "search": {
    "variable": "rate",
    "lower_bound": 1.0,
    "upper_bound": 20.0,
    "duration_seconds": 120
  },
  "runs_per_level": 3,
  "max_levels": 6
}
```

Compiler 将已保存的 SLO 与上述搜索范围转换为 EvalScope SLA 参数，并进行指标单位转换。

## 5.5 关键校验

- 开环 Rate 必须 >0；
- 开环不存在并发输入面，额外提交并发字段必须拒绝；
- `number` 数组长度必须和扫描变量一致；
- 测 TTFT 必须流式；
- `duration` 是 Soft Exit，需要区分调度窗口和最终完成时间；
- 固定 Token 测试要记录 `ignore_eos`；
- 数据集和 Tokenizer 固定；
- Compiler 先按每个 level/run 确定测量请求数和测量时限，再分别计算
  `ceil(requests × warmup_ratio)` 与 `ceil(duration × warmup_ratio)`，最后加上 level 间休息时长求总预算；
  不得先汇总后统一取整；
- 编译结果不得超过总请求、输入 Token、输出 Token 和持续时间预算；
- Compiled DTO 反序列化时必须从 Traffic、Workload 和 Warmup Ratio 重算请求与 Token 估算，拒绝篡改或不一致的 Budget Estimate；
- Raw Report 的 `Submitted` 不得超过 `budget_estimate.measurement_requests`；测量持续时间和成功 Token 数不得超过
  `execution_budget` 硬上限；成功 Token 数还不得超过 `Completed × WorkloadSpec` 固定单请求长度；
- 输出长度的 P99 不得超过 WorkloadSpec 的单请求输出 Token 上限；
- 同一 Trial 的 WorkloadSpec 必须一致；
- Warmup 不计入指标，但逐 run 计入请求、Token 和持续时间预算。

## 5.6 结果归一化

必须记录：

- Submitted；
- Completed；
- Failed；
- Timed out；
- Duration；
- Window Completion；
- RPS/RPM；
- Input/Output Token Throughput；
- TTFT/TPOT/ITL/E2E；
- 输入和输出长度分布；
- Deployment ID 与获批 Deployment Plan Hash；
- Provider Profile Hash 与 Compiled Benchmark Hash；
- 原始报告 Hash。

EvalScope Raw Report 必须同时绑定 Provider Version、Adapter Version、Provider Profile Version、
Provider Profile Hash、Compiled Benchmark Hash、Traffic Mode 和 Raw Artifact。Normalizer 必须根据绑定的
Profile 与 Compiled Benchmark 重新计算 Hash 并逐项匹配；不得用另一份 Profile、单位或 Traffic Mode
重新解释同一份原始报告。

## 5.7 不暴露给 AI

- EvalScope 全部 CLI；
- 任意 `extra_args`；
- 任意 URL；
- 任意 Header；
- 任意数据文件路径；
- 无上限的 Rate；
- 直接修改输出目录。

## 6.3 SearchSpaceSpec

<!-- schema-example: vllm-search-space-v1 -->
```json
{
  "schema_version": "vllm-search-space/v1",
  "profile_name": "balanced-v1",
  "objective": {
    "metric": "successful_output_tokens_per_second",
    "direction": "maximize"
  },
  "slo": {
    "schema_version": "slo/v1",
    "constraints": [
      {
        "kind": "numeric",
        "metric": "ttft_p95_ms",
        "operator": "<=",
        "value": 2000
      },
      {
        "kind": "numeric",
        "metric": "success_rate",
        "operator": ">=",
        "value": 1.0
      },
      {
        "kind": "boolean",
        "metric": "oom",
        "operator": "==",
        "value": false
      }
    ]
  },
  "gpu_memory_utilization": {
    "low": 0.80,
    "high": 0.94,
    "step": 0.02
  },
  "max_num_seqs": [4, 8, 16, 32],
  "max_num_batched_tokens": [2048, 4096, 8192, 16384],
  "enable_chunked_prefill": [false, true]
}
```

`gpu_memory_utilization` 必须形成由十进制精确计算的闭区间网格：`high > low`、区间能被
`step` 整除，且包含端点后最多 15 个值。所有分类选项必须唯一并按稳定顺序排列。枚举时先执行
vLLM scheduler 交叉规则的静态裁剪；若没有任何合法组合，整个 Search Space 直接拒绝。

## 6.4 Trial 流程

```text
Optuna ask
→ Candidate Validator
→ 静态裁剪
→ 部署
→ 健康检查
→ Benchmark
→ Constraint Evaluation
→ MLflow Logging
→ Optuna tell
→ Cleanup
```

## 6.5 Trial 状态

- `suggested`
- `rejected_static`
- `deployment_failed`
- `benchmark_failed`
- `oom`
- `constraint_failed`
- `completed`
- `cancelled`

失败 Trial 也必须保存原因，不可静默消失。

## 6.6 Pruning

Optuna 通用 Pruner 当前主要面向单目标中间值。MVP 第一版不依赖“Benchmark 中途的多目标 Pruning”，采用：

- 静态裁剪；
- OOM 边界裁剪；
- 明显违反硬约束时终止该 Trial；
- 单目标 Objective；
- 约束作为可行性判断。

## 6.7 AI 不可调用

- `trial.suggest_*`；
- `study.tell`；
- 直接修改 Storage；
- 直接决定 Trial 指标；
- 跳过 Benchmark；
- 修改固定模型/数据集。

# 7. 环节六：收敛、选择和证据

## 7.1 选择

主要项目：MLflow Tracking。

准确边界：

- MLflow 存参数、指标、Artifact、Run；
- MLflow 提供查询和比较；
- **你们自研 Champion Policy**；
- AI 只解释，不生成指标。

## 7.2 AI 可见 Tool

### `get_trial_comparison_result`

返回标准化对比表。

### `create_champion_plan`

由确定性 Policy 先筛选并生成不可变 Champion Plan，包含 Champion、Fallback、证据完整性和 Plan Hash。

### `get_evidence_result`

读取已归档的 Evidence Summary，返回 Evidence Bundle 和报告 Artifact Ref。

## 7.3 自动记录，不作为 AI Tool

每个 Run 自动记录：

- Hardware Passport ID/Hash；
- 模型 Revision；
- 镜像 Digest；
- vLLM 参数；
- WorkloadSpec Hash；
- EvalScope 版本；
- 指标；
- 日志；
- 原始报告；
- 失败原因；
- 时间；
- 代码版本。

## 7.4 Convergence Policy

停止条件任一满足：

- Trial Budget 耗尽；
- Wall-clock Budget 耗尽；
- Token Budget 耗尽；
- 连续 N 个有效 Trial 改善低于阈值；
- 搜索空间有效组合耗尽；
- 用户取消；
- 基础设施阻断。

不能因为 LLM 说“差不多了”而停止。

## 7.5 Champion Policy

<!-- schema-example: champion-policy-v1 -->
```json
{
  "schema_version": "champion-policy/v1",
  "top_candidate_count": 3,
  "verification_repeats": 2,
  "max_coefficient_of_variation": 0.05,
  "noise_multiplier": 1.0,
  "minimum_relative_improvement": 0.01
}
```

1. 过滤无效/失败 Trial；
2. 过滤未满足全部硬约束；
3. 过滤证据不完整；
4. 按目标指标排序；
5. 对 Top 3 复测；
6. 计算均值、离散度和最差值；
7. 只有显著超过噪声才宣称更优；
8. 输出 Champion + Fallback；
9. 人工批准。

确定性门禁同时要求：每个候选的 CV 不超过
`max_coefficient_of_variation`；Champion 与 Fallback 的均值差严格大于
`noise_multiplier × (champion_std + fallback_std)`；相对提升
`(champion_mean - fallback_mean) / fallback_mean` 不低于
`minimum_relative_improvement`。最终选择使用 `champion-selection/v2`，并将
`max_coefficient_of_variation`、`noise_multiplier` 和
`minimum_relative_improvement` 作为必填字段持久化；这些阈值不能由 LLM 临时修改。

`champion-selection/v2` 是不向后兼容的持久化契约升级。v1 记录不得作为新的 Champion 审批输入；
历史 v1 Evidence 只读保留，需要重新审批时必须基于原始复测证据按 v2 Policy 重新生成 Selection。
该升级不影响既有 Deployment 或 Benchmark Plan。

# 8. 环节七：安全、策略和审批

## 8.1 选择

主要项目：OPA。

OPA 负责根据结构化输入返回策略决策。它不是执行器，也不是 Agent Tool 的直接替代。

## 8.2 AI 可见 Tool

### `start_approval_request`

AI 可以解释为什么需要审批并发起请求。

### `get_approval_status`

查询人审结果。

`explain_rejected_action` 可以由应用层读取 OPA Reason 后生成，不一定作为独立 Tool。

## 8.3 内部强制能力

- `authorize_action`
- `mask_decision_log`
- `record_decision`
- `enforce_limits`
- `require_plan_hash`
- `require_human_approval`

这些不暴露给 AI。

## 8.4 风险等级

| 等级 | 示例 | 默认 |
|---|---|---|
| L0 | 查询结果、创建只读计划 | 自动允许 |
| L1 | 环境检测、模型元数据解析 | 自动允许并审计 |
| L2 | 启停容器、压测、调优、下载模型 | 人工审批 |
| L3 | 驱动、内核、删除模型、任意 Shell | MVP 拒绝 |
