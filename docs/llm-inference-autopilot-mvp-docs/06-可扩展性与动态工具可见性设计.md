# 06. 可扩展性与动态工具可见性设计

## 1. 扩展目标

未来可能新增：

- AMD/昇腾硬件检测；
- DCGM/NCCL；
- SGLang/TensorRT-LLM/LMDeploy；
- GuideLLM/AIPerf；
- Bento llm-optimizer；
- Kubernetes/KServe/llm-d Runtime/Dynamo；
- 多 GPU、多节点；
- 在线 Trace Replay；
- 质量评测；
- 模型自动推荐。

MVP 架构必须做到：

> 新增 Provider 时尽量不改变 Agent Tool、Graph 和领域数据；新增真正的新业务能力时，通过新的 Capability Package 和 Registry 扩展。

## 2. Ports and Adapters

领域定义 Port：

```python
class DeploymentPort(Protocol):
    def get_capabilities(self) -> DeploymentCapabilities: ...
    def validate(self, plan: DeploymentPlan) -> ValidationReport: ...
    def preview(self, plan: DeploymentPlan) -> DeploymentPreview: ...
    def start(self, plan: DeploymentPlan, context: JobContext) -> DeploymentHandle: ...
    def status(self, handle: DeploymentHandle) -> DeploymentStatus: ...
    def stop(self, handle: DeploymentHandle) -> None: ...
    def logs(self, handle: DeploymentHandle) -> ArtifactRef: ...
```

Adapter：

```text
VllmDockerAdapter
SglangDockerAdapter（未来）
TensorRTLLMDockerAdapter（未来）
VllmKubernetesAdapter（未来）
```

Graph 依赖 `DeploymentPort`，不依赖 vLLM CLI。

## 3. 防腐层

外部项目的术语不能直接污染领域模型。

例如：

- EvalScope 的 `parallel` 在内部映射为 `closed_loop_concurrency`；
- EvalScope 的 `rate` 映射为 `arrival_rate_rps`；
- vLLM 的参数保留在 `EngineTuningSpec`，不进入通用模型业务要求；
- MLflow Run ID 作为 Evidence Provider Ref，而不是 Experiment 的主 ID。

这样更换工具时上层语义稳定。

## 4. Capability Registry

```python
class CapabilityRegistry:
    def register_package(self, package: CapabilityPackage): ...
    def providers(self, capability: str): ...
    def resolve_provider(self, request, environment): ...
    def visible_tools(self, context): ...
    def schema(self, tool_name, version): ...
```

Registry 数据：

```yaml
capabilities:
  deployment:
    default_provider: vllm-docker
    providers:
      vllm-docker:
        adapter: VllmDockerAdapter
        supports:
          hardware: [nvidia]
          topology: [single_gpu]
          api: [openai_chat]
      sglang-docker:
        enabled: false
```

## 5. Provider 选择

MVP 固定 Provider，未来才动态选择。

解析顺序：

1. 用户明确选择且支持；
2. 环境能力；
3. 模型兼容矩阵；
4. Feature Flag；
5. 默认 Provider；
6. 无可用 Provider 时明确失败。

AI 可以建议 Provider，但最终由 Registry 和 Compatibility Rules 决定。

## 6. 动态 Tool 可见性

### 6.1 计算模型

```text
VisibleTools =
PhaseAllowed
∩ RoleAllowed
∩ EnvironmentSupported
∩ ProviderEnabled
∩ PolicyAllowed
∩ FeatureFlagEnabled
```

### 6.2 为什么不是只靠 Prompt

Prompt 中说“不要调用”不能构成安全边界。不可见 Tool 不应发送给模型；即使模型伪造 Tool 名称，Tool Gateway 也要拒绝。

### 6.3 Tool Set 快照

每次 LLM 调用记录：

```json
{
  "schema_version": "tool-set-snapshot/v1",
  "tool_set_id": "toolset_01...",
  "tool_set_version": "sha256:...",
  "experiment_id": "exp_01...",
  "subject": {
    "kind": "human",
    "user_id": "user_01...",
    "role": "operator"
  },
  "phase": "benchmark",
  "hardware_capabilities": ["openai_compatible_endpoint"],
  "enabled_providers": ["evalscope"],
  "enabled_feature_flags": ["benchmark"],
  "tools": [
    {
      "name": "create_benchmark_plan",
      "schema_version": "benchmark-plan-request/v1",
      "risk_level": "L0"
    },
    {
      "name": "start_benchmark",
      "schema_version": "plan-execution-request/v1",
      "risk_level": "L2"
    }
  ],
  "policy_decision_ids": ["opa-decision-1", "opa-decision-2"]
}
```

Tool Set Version 对 Experiment、Subject、Phase、Hardware、Provider、Feature Flag 和排序后的 Tool/Schema/Risk
做 Canonical Hash；OPA Decision ID 不进入 Hash。Agent 后续调用必须同时提交 `tool_set_id` 和预期 Version，Gateway
再与当前持久化 Phase 和可信环境对账，不能只信客户端保存的 Tool 名称。

## 7. Tool 版本化

### 7.1 版本规则

- 新增可选字段：Minor；
- 改变字段语义：Major；
- 删除字段：Major；
- Provider Adapter 可独立版本；
- Plan 中记录 Schema Version 和 Adapter Version。

### 7.2 迁移

旧 Plan 不直接用新 Compiler 执行。

```text
old plan
  ↓ schema migration
new plan draft
  ↓ revalidation
可能需要重新审批
```

## 8. Provider Version Profile

外部工具升级后参数可能改变，因此为每个已验证版本维护 Profile：

```yaml
provider: evalscope
provider_version: "pinned-image-digest"
profile_version: 1

features:
  open_loop: true
  sla_auto_tune: true
  progress_tracker: true

mapping:
  warmup_ratio: warmup_num

constraints:
  ttft_requires_stream: true
  open_loop_ignores_parallel: true

allowed_expert_overrides:
  log_every_n_query:
    type: integer
    min: 1
    max: 1000
```

未注册版本不能自动进入正式实验。

## 9. 新增 Benchmark Provider 示例

新增 GuideLLM：

1. 实现 `BenchmarkAdapter`；
2. 定义 Provider Profile；
3. 将 GuideLLM 结果转换为统一 `BenchmarkResult`；
4. 通过 Contract Tests；
5. 在 Registry 中启用；
6. 不新增 `run_guidellm` Agent Tool；
7. `create_benchmark_plan` 仍然使用同一 WorkloadSpec；
8. 只在 Provider 支持矩阵中显示差异。

## 10. Provider 特有能力

如果 SGLang 有 vLLM 没有的能力，不应强行塞入通用字段。

```json
{
  "engine_extensions": {
    "sglang.radix_cache": {
      "schema_version": "v1",
      "enabled": true
    }
  }
}
```

Extension 要求：

- Namespace；
- Schema；
- Provider；
- Tool 可见性；
- 风险；
- 兼容性；
- 不影响不支持的 Provider。

## 11. Feature Flags

```yaml
features:
  expert_override: false
  multi_gpu: false
  kubernetes_deployment: false
  sglang_provider: false
  production_trace_replay: false
```

Feature Flag 影响：

- Tool 可见性；
- Schema；
- UI；
- Registry；
- 测试矩阵。

不应只影响前端按钮。

## 15. Contract Tests

每个 Adapter 必须通过：

- Capability；
- Input Validation；
- Plan Compilation；
- Start/Status/Cancel；
- Result Normalization；
- Error Mapping；
- Idempotency；
- Artifact；
- Version Profile。

Fake Adapter 用于 Graph 测试，避免每次都占 GPU。

---

## 16. MCP 是否使用

未来可以提供 MCP Server，让 Codex/OpenCode 或其他 Agent 使用领域能力。

但核心原则不变：

- MCP 只是传输/发现接口；
- 工具仍经过 Tool Gateway；
- MCP 不直接暴露 Runner；
- 不提供任意 Shell；
- 使用相同 Schema、OPA 和审计。

首版内部可直接 Function Tool，暂不必为了 MCP 增加复杂度。
